# NuGet Supply Chain Defense (.NET 10)

Companion repo for the article *"NuGet Supply Chain Attacks: How Malicious
Packages Compromise Your .NET Build Pipeline (and How to Stop Them)"* on
[adrianbailador.github.io](https://adrianbailador.github.io).

Two things are demonstrated end to end, with tests, not just described:

1. **The attack surface is real.** A NuGet package can run arbitrary MSBuild
   logic the moment you `dotnet build` — no call from your own source code
   required. `src/EvilPkg.Benign` is a package that does exactly this.
2. **It's blockable with configuration alone.** `src/DefensiveApp` uses
   `packageSourceMapping`, a committed lock file, and central package
   management; `src/VictimApp` doesn't. Same dependency, same attack,
   different outcome.

## Scope and safety

This is a **lab-only, local-only** demonstration, not a working exploit:

- `EvilPkg.Benign`'s payload only writes one line to a local text file —
  `supply-chain-poc-marker.txt` — with a timestamp and the current OS
  username. No network call, no credential access, no persistence, no
  second-stage anything.
- It is never published to nuget.org or any public feed. It only ever exists
  in `local-lab-feed/`, a plain folder on disk that NuGet treats as a package
  source — see `src/*/NuGet.config`.
- Nothing here targets a real system, account, or package that isn't part of
  this repo.

If you're looking for a real attack to run against someone else's
infrastructure, this isn't it, and that isn't what this repo is for.

## Layout

| Path | Role |
|---|---|
| `src/EvilPkg.Benign` | The PoC package. `buildTransitive/EvilPkg.Benign.targets` is the actual payload — everything else is packaging boilerplate. |
| `src/VictimApp` | References `EvilPkg.Benign` with no mitigations. `NuGet.config` has no `packageSourceMapping`. |
| `src/DefensiveApp` | Same .NET 10 console app shape, but `NuGet.config` maps every package to an explicit source/prefix, `RestorePackagesWithLockFile` is on, and the solution uses central package management (`Directory.Packages.props`). |
| `tests/SupplyChainDefense.Tests` | Shells out to the real `dotnet` CLI against an isolated copy of the repo (its own temp dir, its own `NUGET_PACKAGES` cache) and asserts both outcomes. |
| `local-lab-feed/` | Local, folder-based NuGet source. Empty in git — regenerated by the test fixture or `scripts/build-lab-feed.sh`. |

## Running it

```bash
dotnet test tests/SupplyChainDefense.Tests/SupplyChainDefense.Tests.csproj
```

(Scoped to the test project on purpose — the fixture packs and copies
everything else into its own isolated temp dir, so this never needs
`local-lab-feed/` populated at the repo root first. A plain `dotnet build`
or `dotnet test` at the repo root *will* fail until you run
`scripts/build-lab-feed.sh`, because `VictimApp` and `DefensiveApp` are real
projects that need the package to exist somewhere.)

This packs `EvilPkg.Benign` fresh into an isolated temp copy of the repo and
runs both scenarios:

- `VictimApp_without_source_mapping_executes_the_dependency_build_logic` —
  builds `VictimApp` and asserts the marker file appears.
- `DefensiveApp_with_source_mapping_refuses_to_restore_the_same_package` —
  adds the same `PackageReference` to `DefensiveApp`, restores, and asserts
  NuGet refuses with `NU1100` before any build-time logic runs.

To reproduce either side by hand:

```bash
./scripts/build-lab-feed.sh        # packs EvilPkg.Benign into local-lab-feed/
cd src/VictimApp && dotnet build    # marker file appears — nothing in Program.cs asked for it
cat supply-chain-poc-marker.txt
```

## What this maps to in the article

- Package source mapping as the actual control, not a checkbox — including
  the pitfall that a pre-populated global NuGet cache (`~/.nuget/packages`)
  can mask whether mapping is working, because an already-cached package
  version doesn't get re-validated against sources on every restore.
- `RestorePackagesWithLockFile` + locked-mode restore for reproducibility.
- Central package management (`Directory.Packages.props`) and the
  `VersionOverride` escape hatch, which is also where an unreviewed PR can
  reintroduce exactly this risk if nobody is watching for it.
